# Cocreo（@cocreojp）X運用の再設計

作成日: 2026-08-04
対象: X アカウント @cocreojp / 投稿生成ツール `agentdx` / Cocreo のプロダクト訴求
方法: マーケター・保険代理店の現場ユーザー（経営者/事務/若手募集人）・デザイナーの3視点で2周の相互批評を実施し、対立点を裁定した

---

## 0. 結論（先に3行）

1. **閲覧数が伸びない主因は投稿内容ではない。** フォロワー1では配信先が物理的に存在せず、投稿の質は評価の第2段階以降でしか効かない。投稿を改善しても閲覧数は比例しない。
2. **Xで本命顧客を捕まえる戦略そのものが誤り。** 中小専業代理店の経営者・内勤事務はXにいない。Xの役割を「見込み客獲得の場」から**「転送される1枚を置く在庫棚」**に再定義する。
3. **カード画像は本番で日本語が表示されていない可能性が高い（要実機確認）。** 画像付きで投稿していた期間があるなら、閲覧数以前の問題として文字化けした画像を業界関係者に見せていたことになる。

## 1. 検証で判明した事実

### 1-1. 【最優先】生成カード画像の日本語が本番で豆腐化している疑い

`server/src/routes/agentdx.js:528`

```js
const JP_FONT = 'Hiragino Sans, Noto Sans JP, sans-serif';
```

- Hiragino Sans は macOS 専用。**Noto Sans JP は Render の Node ランタイムに含まれない**
- `render.yaml` は `runtime: node`。リポジトリ全体に Dockerfile / aptfile / `fc-cache` / フォントファイルが**1つも存在しない**（確認済み）
- 同種の Linux 環境で `fc-match` を実行した結果:

  ```
  fc-match "Noto Sans JP"  → DejaVuSans.ttf
  fc-match "Hiragino Sans" → DejaVuSans.ttf
  fc-match sans-serif      → DejaVuSans.ttf
  ```

  DejaVu Sans は CJK グリフを持たない。`sharp` はサーバ側で SVG をラスタライズする（`agentdx.js:638`）ため、**日本語は豆腐（□）または空白になる**
- `agentdx.js:558` のワードマーク "Cocreo" だけ `font-family="Arial"` 指定なので、そこだけ読める
- ローカル macOS では Hiragino が効いて正常に見えるため、**本番だけ壊れる**発覚しにくい形になっている
- `AgentDxHome.jsx:120,154,192` で転換系は画像を自動生成し、`agentdx.js:698-703` は `image_path` があれば無条件に添付する。**気づかないまま投稿される**

> 厳密には Render 実機での確認は未実施。フォント解決の仕組みを同等環境で確認した結果であり、実機確認が必要。

**まず過去の投稿画像を目視確認すること。** 文字化けしていた場合、画像投稿を即時停止する。

### 1-2. ブランドカラーがコード内で3系統に分裂

| 出典 | 値 | 用途 |
|---|---|---|
| `insurance-news/support.html:11-13` | `#F26522` / `#D4541A` / `#FFF3EE` | Xヘッダーと一致 |
| `client/src/index.css:7` | `#C9891F`（金茶） | アプリUI |
| `agentdx.js:522-526` `CARD_PALETTES` | violet `#6d28d9` / blue / emerald | 投稿カード |

さらに `AgentDxImageStudio.jsx:6` は violet に **`label: 'Cocreo'`** を付けている。コード上で「Cocreo＝紫」と宣言されている状態。

**裁定：外向き素材は `#F26522` に単一化する。** マーケターは `#C9891F` を主張したが、アカウントのヘッダー・LPが既に `#F26522` で運用されており、外から見えている identity はオレンジである。`#C9891F` はアプリUI内に留め、`CARD_PALETTES` の紫・青・緑は破棄する。

> **要確認**: 若手募集人Cから「オレンジは保険業界だと某社を連想する色。認証バッジがある分、公式と誤認されるのは危ない」との指摘があった。`#F26522` 確定前に、主要保険会社のコーポレートカラーとの近似を目視で確認すること。

### 1-3. アナリティクスが1バイトも取れていない

`server/src/database.js:139-151` の `sns_posts` テーブルに `impressions` 系カラムが1本もない。**改善ループが構造的に回らない状態**。何が効いて何が効かないかを判断する材料が存在しない。

## 2. 現場の証言（意思決定に直結するもの）

3名の想定ユーザー（A=6名規模乗合代理店の経営者50代 / B=同社の事務担当30代 / C=若手募集人30代）による評価。

### 2-1. フォローされない理由は、投稿ではなくアカウントの状態

> **A**「フォロワー1のアカウントを自分が2人目としてフォローするのが怖い。フォロー欄は保険会社の支社担当も見ている。『あそこの社長、どこのAI業者に捕まったんだ』と思われるのが一番嫌」

**フォロワー数そのものが参入障壁になっている。** かつこの層はX内では増やせない。X内でのフォロワー増努力は費用対効果が最悪であり、放棄する。

### 2-2. 固定ポストの「生損保の商品比較」はコンプラ地雷

> **A**「SNS上の実名商品比較は募集文書等に該当し得るうえ、各社の審査を通っていない。保険会社のコンプラ部門はSNSを見ている。**実名比較を一度でも出したアカウントは即フォロー解除する**」

現在の固定ポストは「生損保の商品比較」を看板の1つに掲げている。**これがある限り、本命顧客はコンプラ上の理由でフォローできない。** 即日外す。

### 2-3. 型D（制作実況）の「教えてください。作ってみます」は構造的に成立しない

| | 返信するか | 理由 |
|---|---|---|
| A（経営者） | しない | 「公開の場で自社の体制整備の穴を、金融庁と保険会社に向けて自白するのと同じ」 |
| B（事務） | しない | 「公開で答えたら、社長への不満表明に見える」 |
| C（若手） | したいができない | 「フォロワー1のアカウントに最初のリプを付ける＝晒し台。返信欄に自分だけがいる絵を想像すると指が止まる」 |

**返信を集めるエンジンとして設計された型Dは、この業界では機能しない。**

### 2-4. iOSアプリは事務担当の動線に存在しない

> **B**「仕事は100% Windowsのデスクトップ。申込書を見て、保険会社のポータルに入力して、Excelを開く。この動線にスマホが入る余地がゼロ。**Excelアドインかブラウザで動くものにしてくれたら、私は明日使う**」

> **A**「支給端末はiPhoneだが、顧客情報を扱う関係でアプリの自由インストールは事実上禁止」

これはマーケティングの問題ではなく**プロダクトの問題**。X の投稿設計より優先度が高い。

### 2-5. 効率化訴求が事務担当を敵に回している

> **B**「『40分→3分』を見て最初に思ったのが『じゃあ私の仕事、要らないってこと？』でした。ここ、作り手が分かってない気がします」

導入を決めるのは経営者だが、**使い続けるかを決めるのは事務担当**。現在の訴求は後者を敵に回している。

### 2-6. 情報源としてのXの順位は5番目以下

Aが実際に見ている場: ①保険会社の支社担当 ②保険毎日新聞・新日本保険新聞 ③日本代協の支部会・研修 ④保険会社の代理店会 ⑤同業10人の勉強会LINE ⑥inswatch

> **A**「Cocreoさんがやるべきは、Xで私を捕まえることではなく、**勉強会LINEに転送されるスクショを作ること**」

Aが唯一「保存して勉強会LINEに転送する」と言ったのは**型B（セルフチェック）のみ**。ただし条件付き:

> 「2026年改正と書くなら**条番号か金融庁の資料名を1行入れてほしい**。出典がないものを社内に配ると、私が責任を取ることになる」

**転送されるかどうかを決めているのは内容の質ではなく、転送した本人が守られるかどうか。**

## 3. 戦略の再定義

### 3-1. Xの目的を変更する

| | 旧 | 新 |
|---|---|---|
| 目的 | 見込み客の獲得 | **転送可能な1枚を置く在庫棚** ＋ 業界メディア・ベンダーに発見される場 |
| 求める行動 | 返信・フォロー | **保存・スクショ・転送**（すべて非公開行動＝A/B/C全員のリスクを回避できる唯一の経路） |
| 主KPI | フォロワー数・インプレッション | **ブックマーク数**（保存＝転送の代理指標） |
| 最終閲覧環境 | XのTL | **LINEグループに転送された画像** |

### 3-2. 労力配分

| 領域 | 配分 | 内容 |
|---|---|---|
| **プロダクト** | 35% | Web/Excel版への移行（2-4が理由） |
| リアル | 25% | 日本代協支部会、保険会社の代理店会、勉強会でのLT |
| 業界メディア | 20% | inswatch・保険毎日新聞・新日本保険新聞への寄稿 |
| note | 10% | 検索流入とメディアへのネタ元 |
| **X** | 10% | 転送用アセットの置き場 |

Aが挙げた受け入れられる露出の形（優先順）:
1. **inswatchへの寄稿**「あそこに名前が載っていれば、業界の人として扱う」
2. **支部会・勉強会でのLT**。条件は「**自社ツールの宣伝をしない20分**。法改正の実務対応を話して、最後の1枚だけ『こういうものを作っています』。逆でやると即死」
3. 支社担当からの又聞き

白ける形（やってはいけない）: 代理店会の懇親会で名刺を配る / 協会名簿を使ったDM・メール / **勉強会LINEに本人が入って宣伝する**（招き入れた人の信用が減るため、招待されることは永久にない）

### 3-3. 撤回した施策

議論の過程で提案され、反証により破棄したもの。同じ案が再浮上したときのために記録する。

| 施策 | 破棄理由 |
|---|---|
| リプライ営業 1日10件×30日=450件 | A「保険業界のXは狭く、同じ人が方々にリプしているのが完全に見える。3日で『あの人また出てる』、1週間で勉強会LINEにスクショが回る。**露出ではなく風評の生成**」。C「120字以上の縛りは逆効果。私の投稿の返信欄がその人の宣伝枠に見える」 |
| 型Dを主力に据える | 2-3のとおり返信が構造的に発生しない |
| Blue の長文投稿を活用 | 1画面に収まらず、スクショ転送戦略と矛盾 |
| フォローバック後のDM営業 | A「開くが返さない。返すと断る手間が発生する。**DMで来る時点で、この人はうちの意思決定を知らないと分かる**」 |
| 保険会社ポータル画面・申込書のスクショ | A「規程で複製・外部公開が禁止。**ぼかしても駄目**。画面の配色とレイアウトだけで同業には一発で分かる」 |
| カード画像4テンプレの全面改修 | 3テンプレは削除する（5-2） |

## 4. 投稿設計

### 4-1. 固定ポスト（差し替え文面・このまま投稿可）

```
保険業界20年、代理店の内勤と募集を両方やってきました。
いまは代理店の実務を軽くするツールを自分で作っています。

・法改正と監督指針の改正点を「現場で何を確認するか」に翻訳
・意向把握と比較推奨の"記録"の残し方チェックリスト
・申込書と告知書まわりの転記手順の整理

個社の商品比較はしません。商品の優劣も扱いません。
扱うのは、当局と保険会社に説明できる状態をどう作るか、だけです。

チェックリストは出典（条番号・監督指針名）付きで出します。
社内の勉強会やLINEに、そのまま転送していただいて構いません。

ご相談は cocreo.jp から。こちらから電話はしません、メールのみです。
```

設計意図:
- 「商品比較」を看板から外し、比較の主語を**商品からプロセス（記録）へ**移した
- 最終行はAの「押した瞬間に電話がかかってくるボタンに見える。反射的に閉じる」への直接の解毒
- 「転送していただいて構いません」と明示的に許可を出す（転送のハードルを下げる）

**さらに改善余地（Aの指摘）**:
- 「保険業界20年」が誰の20年か不明。代理店側・保険会社側・ベンダー側で信用度が全く違う。「損保プロ代理店で15年、うち5年は乗合の体制整備担当」レベルの具体性が必要
- 「AIで◯分」と言い切らない。「読み取り精度は9割、残り1割は人が直します」と**弱点を先に書く方が信じられる**

### 4-2. プロフィール

- **表示名**: `Cocreo` → **`Cocreo｜保険代理店の事務をAIで減らす`**（アイコンで社名は読めないため、名乗りは表示名に委譲する）
- **bio 1行目**: 「保険業界20年の実務者 → 代理店向けAIを個人開発中」
- **ヘッダーの「AI導入のご相談はこちら→」バナーを削除**。押せないものをボタンの形にするのはB2Bで信用の減点であり、Aも「反射的に閉じる」と証言。テキストで `↓ プロフィールのリンクから` に置換

### 4-3. 型B（セルフチェック）を主力にする

Aが唯一「転送する」と言った型。要件:

- 全角380〜450字（iPhone縦1画面の上限）
- **末尾に出典1行を必須化**: `（出典：保険業法第294条の3／金融庁「保険会社向けの総合的な監督指針」II-4-2-2）`
- **「要約は私の解釈です。社内で使う際は原文をご確認ください」を必ず添える**。Aいわく「この最後の1行が命。これがないものは、どんなに正しくても転送しない」
- 実名商品・保険会社名・優劣表現はゼロ。保険会社は `A社／B社／C社` に統一（コンプラ回避であると同時に、読者が自分の乗合先に置き換えられる利点がある）
- 末尾に**版数**（「2026年8月版」）を入れる。転送経路を測る唯一の実測手段になる

Aが作成した「転送したくなる投稿」の完成形:

```
【2026年改正・体制整備】朝礼で読める3行にしました。

金融庁が今年の監督で代理店に見ているのは、要するにこの3つです。

1. 意向把握を「した」ではなく「どう記録したか」
2. 比較推奨の理由が、募集人の頭でなく書面にあるか
3. 募集人任せの部分を、代理店として管理しているか

出典：金融庁「2025事務年度 保険モニタリングレポート」P.◯◯／保険業法294条の3
※原文の該当箇所は画像2枚目にそのまま貼っています。
　要約は私の解釈なので、社内で使う際は原文をご確認ください。
```

### 4-4. 型D（制作実況）の本文ルール改訂

`server/src/services/claudeService.js:395` の型D定義に、**第4項「削った時間で何ができるようになったか」を必須化**する。Bの「私の仕事が要らないのか」は画像ではなく本文の問題であり、テンプレを直しても本文が変わらなければ解決しない。

Bが「これなら自分から社長に見せる」と評価した文面:

```
「転記が減る」と書くと、事務の方に嫌われます。

実際に導入した代理店で何が起きたかというと、
事務の方の仕事が減ったのではなく、中身が入れ替わりました。

打ち直し40分 → 3分。
浮いた37分は、不備返戻の事前チェックに回っています。
「この項目、A社は返ってきやすい」という判断は、
今のところ人にしかできません。

だからこのツールは、事務の方の仕事のうち、
いちばんつまらない部分だけを引き受けます。

導入を決めるのは経営者ですが、使い続けるかを決めるのは事務の方です。
だから最初に見ていただきたいのは、社長ではなくその方です。
```

> **B**「最後の2行がすべて。一番言われたいのは『あなたの判断は機械にできない』で、その次が『私に決定権がある』。この2つが書いてあれば、私は味方になります」

### 4-5. 「1件目のリプは晒し台」問題への対処

Cが挙げた、実行してほしい順:

1. **運営者が自分で返信欄の1件目を埋めておく。**「例えばこういう回答が来ています：『満期更改の突合が重い』」と書くだけで2件目になれる。**2件目のハードルは1件目の10分の1**
2. **選択式にする。**「①転記 ②満期更改 ③設計書の追客 ④その他。番号だけでOKです」— 番号1文字なら恥ずかしさがほぼゼロ
3. **「DMでも匿名フォームでも構いません」と毎回書く。** 公開で自社の穴を言えない事情を、運営者が理解していると明示する
4. **返信した人に、後で作ったものを名指しでお礼する。**「◯◯さんの一言で作りました」が一度でも見えれば、次から返信欄は埋まる

## 5. ビジュアル設計

### 5-1. 転送先はXではない — 版面を1080×1350に変更

| 環境 | 表示幅 | 1080px幅画像の倍率 |
|---|---|---|
| LINEトーク内サムネイル | 240〜300px | 0.259x |
| **LINEタップ拡大（iPhone 390pt）** | 390px | **0.361x（律速）** |
| X TL（モバイル単一画像） | 約510px | 0.472x |

現行の1200×675テンプレは本文36px（`checklist` の `size: 36`）＝実効13.0px CSS で**転送先では読めない**。

確定仕様:
- **キャンバス 1080×1350（4:5）**。675→1350で縦領域が2.0倍になり、3項目＋出典行が入る
- **内容を担う文字の下限 40px**（40px未満はラベル記号のみ）
- 1枚あたり**6ブロックまで**（見出し1＋項目3＋判定1＋出典1）
- サムネイル時の役割は読ませることではなく**形で識別させること**。□が3つ縦に並ぶシルエットで「チェックリストだ」と分かることが転送の入口

### 5-2. テンプレートの取捨

| テンプレ | 判断 | 理由 |
|---|---|---|
| `quote` / `number` / `beforeafter` / `checklist` | **全削除** | `number` は幅推定係数 `0.62` が破綻し長い文字列でキャンバス外にはみ出す。`beforeafter` はテキストがパネルから32pxはみ出し、赤緑のハードコードで accent を無視し、かつ2型色覚で最も判別しづらい組。`quote` は44字スライスと14字×3行のオフバイツーで末尾2文字が常に消える。**直さずに消す** |
| **`lawcheck`（新規）** | **作る** | Aが唯一「転送する」と言った型Bの専用版面。出典帯を独立させ、`fields.sourceLabel` 未指定なら生成不可にしてAの条件をコードで担保する |
| `timeshift`（`beforeafter` の後継） | 設計のみ・実装凍結 | 3カラム化（今／AIが代わる部分／**空いた時間でできること**）で面積比 1:1:1.4、見出しを gained 側に置く。ただし4-4の本文ルール改訂が先 |
| `screenshot` | コンプラ確認まで凍結 | 5-4参照 |

```js
  // ライトTLで塊として立つ暗色（型D/実況向け）
  ember: { mode:'dark',  bg:'#17100B', panel:'#241A12',
           ink:'#FFFFFF', sub:'#D8CFC7', accent:'#FB923C', rule:'#F26522' },
};
```

コントラスト実測: `#1A1613` on `#FFF7F2` = 16.8:1 / `#D4541A` on `#FFF7F2` = 4.6:1 / `#FFFFFF` on `#17100B` = 18.9:1 / `#F26522` on `#000` = 4.96:1、on `#FFF` = 3.81:1（**両TL背景で縁が立つ**）。

運用ルール: **カード端に高さ8〜12pxの `#F26522` ベタ帯を必ず引く。** paper がライトTLに溶けず、ember がダークTLに溶けない。1画像で両モードを担保する最小コストの仕掛け。

`beforeafter` の赤緑は全廃し、Before `#8E867D` / After `#F26522` に（色覚に依存せず、After＝ブランド色という意味の一致も取れる）。

### 5-4. スクショに写してよいもの／絶対に駄目なもの

| 対象 | 可否 | 根拠 |
|---|---|---|
| 保険会社のポータル画面 | **絶対不可** | システム利用規程で複製・外部公開が禁止。ぼかしても意匠で会社が特定される |
| 申込書 | **絶対不可** | 保険会社の帳票かつ募集文書。様式番号や罫線の癖で特定される |
| **Excel** | **可（最強）** | 自分で作ったファイル。「左=見慣れたExcel、右=ツール画面」はExcelに限れば正解 |
| 複合機の紙束・FAX受信ランプ | 可 | 保険と無関係な物体。「うちの業務だ」度は最高 |
| 手書きの付箋・チェック用紙 | 可 | 同上 |
| 自作ツールの画面 | 可 | 自社資産 |

**ダミーデータについては専門家の直感が逆だった。**

> **A**「現場では『ダミーデータで作りました』と明記されている方が信用が上がる。本物の顧客データが入った画面を出す人は、その瞬間に『情報管理が甘い代理店』の烙印を押される。**作り物に見える心配より、本物を出す恐怖の方が100倍大きい**」

推奨: 画像内に小さく「架空データです」と明記する。伏せ字（山田◯◯）ではなく**記号化（`契約者A`）**を使う。伏せ字は隠蔽に見え、記号化は資料に見える。**数字だけは実測値を使う。**

> **B**「Excelでも列名は要注意。『保険会社名』列にA社B社の実名が入っていたら比較表に見える。**列名だけ見せて中身は伏せる**のが安全」

### 5-5. アイコン

現状は白地に「Cocreo」6文字。48px円内で判読できるラテン文字は1字あたり最低10px幅が必要＝**上限3文字**。6文字は1字8px以下となり、どう組んでも読めない。ダークモードでは白円が「何かの空白」に見え、ライトモードではTL背景と同色で輪郭が消える（**両モードで別々の理由で失敗している**）。

**確定案**: `#F26522` ベタ地 ＋ 白 `#FFFFFF` の **「Co」2文字のみ**、weight 800、字高を円直径の38%（400×400書き出しで152px）、字送り -2%。48px時の実効字高18px、32px時12px で両サイズ判読可能。炎マークは併置しない（2要素は32pxに入らない）。書き出しは400×400 PNG（現状2000×2000はXが再圧縮するため無駄）。

> **A**「アイコンに社名が書いてあるアカウントは業者に見える。個人でやっている人は顔か抽象マーク、業者はロゴ、というのが私の中の分類」

Aの懸念の実体は「社名が読めない」ではなく「**誰か分からないアカウントを信用できない**」であり、32pxのアイコンでは解けない。社名の可読性は表示名（4-2）に委譲する。

### 5-6. ヘッダー

X ヘッダー1500×500 の実効セーフエリアは **`x 480–1440, y 110–330` の 960×220 のみ**（上端0–90pxに戻る/検索アイコン、左下 x 0–420 / y 300–500 にアバターが食い込む）。スクショで「AIで支援する」の左が読めないのはこれが原因。

- 要素を4つ（主コピー/サブコピー/イラスト/CTAバナー）→**2つ**に削る。960×220に入るのは主コピー1行＋サブ1行が限界
- 主コピーは全角14〜16字を1行、56px（16字=896px で960幅に収まる）。サブは28px×24字以内
- **イラストを左に移す**。左下はどうせアバターに隠れる。隠れて構わない装飾を左、読ませる文字を右
- 地色は `#FFF3EE` 維持可。ただしアバターをオレンジ地にすることが前提（現行の「白アバター×白〜クリームヘッダー」は分離ゼロ）
